# Design — one real session, driven end to end (ROADMAP-v0.10 item 5)

Committed BEFORE implementation. §6 registers the predictions and discloses
exactly what was already known when this note was written, because a
prediction registered after its experiment is not a prediction.

## 1. What the item asks, and what would be cheating

> Drive at least one real ingestion-or-code session end-to-end through the
> harness (boot matrix → need dispatch → open authoring/WRITE), degrading to
> ASK where the request is unparseable. […] **Acceptance:** one real,
> non-trivial session recorded end-to-end that produces or revises a node
> through the audited route, with the ASK-not-guess contract holding.

The cheat this design refuses: a scripted narration that *reports* a session
without the components actually running. Every leg below calls the shipped
code — `harness.CoreSession.boot`, `dispatcher.NeedDispatcher`,
`external_verifier`, `write_stage.accept_write` — and the transcript is
emitted from the components' own structured records
(`SessionEvent`, `DispatchEvent`, `StagingRecord`, `AcceptanceRecord`,
verdict JSON), never re-typed prose. A leg that cannot run is recorded as a
refusal, not narrated as a success.

Second cheat refused: a session that only *stages*. The acceptance says
"produces or revises a node", so the accepted leg goes all the way through
`accept_write` — seed written, corpus regenerated by trusted code, receipt
left — and the corpus count moves.

## 2. The session, three legs

One session object, one `session_id`, one frame executor, three needs. The
legs are chosen so the session exercises the WRITE gate's *decision*, not
just its happy path.

**Leg A — ACCEPTED authoring, verifier-backed.** The need is a statement the
corpus does not have: `lean_workbook_22080`, `(2^30) % 1000 = 824`, from the
already-pinned Lean-workbook extract. It is ground and decidable in core
Lean, and it exercises **MOD** — the ground-arithmetic fragment's *other*
operator, where v0.10 item 2's first bridge used DIVIDES. The chain:
external verifier PASS over a pinned source → traced transitions → manifest
pin → candidate seed → `accept_write` → corpus regenerated → receipt.

**Leg B — REFUSED authoring, and the refusal is the point.** The need is
`lean_workbook_26313`, `(2^2006) % 7 = 4` — the same *shape* as Leg A, also
true, and NOT provable under the shipped toolchain options (the exponent
exceeds `exponentiation.threshold`, so `decide` closes it with `sorryAx`,
which item 2's axiom audit catches). The session must fail to mint a node
here, record the FAIL verdict, and leave the working tree byte-identical.
A session that only shows its accept path has not shown a gate.

**Leg C — ASK, not guess.** The roadmap's own adversarial probe, "why did
the chicken cross the road?", submitted as a need no registered path claims.
The session must terminate in an abstention or a rendered need, never in
fluent unregistered content marked VERIFIED, and must produce no node.

## 3. The transcript: a committed, deterministic artifact

`experiments/harness_session.json`, written LF with sorted keys and **no
timestamps and no random session id** — the same rule item 2 put on verdicts,
for the same reason: a transcript that cannot be regenerated byte-identically
is a story about a session, not a record of one. Determinism requires:

- the session id is **supplied** by the driver (a fixed value in the
  committed run), not `secrets.token_hex`; the driver passes it explicitly
  rather than monkeypatching, so nothing in `harness.py` changes shape;
- every path in the transcript is repository-relative (item 2's `_relativize`
  lesson: absolute paths make a committed record reproducible on one machine);
- capability-matrix rows are recorded as `(subsystem, liveness)` pairs, so a
  machine WITHOUT Lean records `lean: off` and the transcript still
  regenerates — with Leg A recorded as REFUSED-for-missing-toolchain rather
  than silently skipped.

`scripts/session_run.py` is the driver; `--check` re-runs it and compares
bytes against the committed transcript (the same shape as `recheck`).

## 4. What this slice does NOT claim

- Not a new surface: no REPL, no HTTP skin. Phase 4 is not this item.
- The boot matrix is **liveness only** — a green row is not evidence that a
  verifier is sound (docs/DESIGN-interactive-harness.md §3.2), and the
  transcript repeats that where it prints the matrix.
- The ASK leg demonstrates the contract on ONE unparseable prompt. It is not
  a claim that every unparseable prompt abstains; P-IH4's dispatcher test
  owns the general claim.

## 5. Where the corpus moves

Leg A adds one node, `numbertheory.ingested.lean_workbook_22080`: corpus
253 → 254, `verified_by` links 17 → 18. GC4 pins will move again by the same
denominator dilution item 2 adjudicated (one more fully-ground, owner-less
node), and if they do, a FIFTH append-only registered acknowledgment is
written — never touching the prior four. `group_counts` is predicted
unchanged (a sixth twin null).

## 6. Registered predictions

Disclosure of what was already known when this was written: item 2 probed
that `13 ∣ 2^30 + 3^60` elaborates under core v4.32.2 with axioms
`[propext]`, and that an exponent above `exponentiation.threshold` (256)
makes `decide` fall back to `sorryAx` (that is how `lean_workbook_10411`
became a committed FAIL). **P1 and P2 below are therefore derived from a
known rule, not fresh probes — but neither statement has been run.** No leg
of the session has been executed at the time of writing.

- **P1** — Leg A's verifier check PASSES: `(2^30) % 1000 = 824` elaborates
  under the pinned toolchain with axioms exactly `[propext]`, and the
  correspondence rung adjudicates the new node CORRESPONDS via `canonical`
  with `ambiguous_with` EMPTY, translating `%` to the MOD head.
- **P2** — Leg B's verifier check FAILS with `sorryAx` in the axiom
  footprint, and `stage_write` REFUSES the candidate. The working tree after
  Leg B is byte-identical to before it (`working_tree_digest` unchanged).
- **P3** — Leg C reaches a terminal stop that is an abstention or a rendered
  need; no `verified_by` is minted, no seed is written, and the rendered
  need (if any) is produced by the subsystem-agnostic renderer, not by a
  branch on subsystem id.
- **P4** — The whole-tree delta of Leg A's acceptance is EXACTLY the two
  files the gate declares (the seed and its regenerated corpus), plus the
  receipts under `staging/`; nothing else in `scripts/`, `prover/`,
  `schema/` or the root moves.
- **P5** — `python scripts/session_run.py --check` reproduces the committed
  transcript byte-for-byte on a re-run.
- **P6** — Corpus 253 → 254 and links 17 → 18; `group_counts` unchanged (a
  SIXTH consecutive twin null); GC4 aggregate movement, if any, is pure
  denominator dilution with no constituent moving on any channel —
  adjudicated against the pin file, with the fifth acknowledgment appended
  only if a pin actually moves.
- **P7** — `check_regeneration` still reports byte-identical output after
  the accepted write: the node in `data/` is exactly what the COMMITTED SEED
  emits, not what the candidate claimed.
